# Data Provenance

Every table in this project carries a `source_type`. These are the only four values that exist, and this is what each one actually means here — checked against the real access requirements of each source, not assumed.

## historical_broadcast — SoccerNet action-spotting labels

**What it is:** Real event annotations (goal, card, substitution, and 14 other action classes) for real, played, broadcast football matches, with real in-match timestamps (half + MM:SS). Published by the SoccerNet research consortium.

**What it is not:** Live. These are archival broadcasts, some years old. Nothing in this project ever calls this data "live" — it is labeled Historical Broadcast Data everywhere it appears, including in the agent's own responses.

**Access, verified directly:** The label files (`Labels-v2.json`) are public with zero registration, zero password, zero NDA — confirmed against SoccerNet's own PyPI package documentation. The raw broadcast *video* files are separately gated behind a Hugging Face account + NDA form; this project does not touch the video files, only the label/annotation layer, so nothing here required signing anything.

**Why this is enough:** A "playback data / OTT / broadcast" capability is about being able to model, query, and reason over structured broadcast event data — not about having decoded video frames. Real timestamped event data at match-and-half granularity supports every SQL/BI capability this project demonstrates.

## current_delayed — football-data.org free tier

**What it is:** Real fixtures, results, and league tables across 12 real competitions (Premier League, La Liga, Champions League, World Cup, etc.), refreshed as real matches are actually played.

**What it is explicitly not:** Live/in-play scores. football-data.org's free tier delays scores and schedules; true real-time livescore feeds are a paid tier we are not using. Calling this "live" would be a fabrication the whole rest of this project is built to avoid — so it is labeled **Current/Delayed Source Data**, never "live," anywhere it surfaces (schema, BI, agent responses).

**Access:** Free API token via email signup, no payment, no approval wait — the user does this themselves (same pattern as the earlier Supabase signup).

## real_research — LIVE Wild Compressed Video Quality Database (obtained)

**What it is:** 315 real videos, each carrying a real human subjective quality score (`score.csv`) from actual viewer studies run by UT Austin's LIVE lab. The filename itself encodes real structured metadata: a distortion-type letter code (`o`=pristine reference, `c`=compression, `i`=interlacing, `d`=frame drops, `j`=judder, `f`=flicker, `a`=aliasing) and a nominal resolution tag. One of the two papers this dataset is drawn from — Shang et al., "Assessment of Subjective and Objective Quality of Live Streaming Sports Videos," PCS 2021 — is literally about live sports streaming QoE, which makes this a direct match for a live sports-streaming use case, not a generic stand-in.

**What we actually ingest:** `score.csv` and the filename-encoded metadata — not the 315 raw video files themselves. The analytical/BI/agent layer needs the structured signal (which distortion type, at what severity, produced what human-perceived quality score), not decoded video frames. Downloading all 315 source videos is optional and deferred; nothing in this project's SQL, Power BI, or agent layer requires them.

**Required citation (license terms, not optional):** Any publication or portfolio write-up using this data must cite both:
- Z. Shang, J. P. Ebenezer, Y. Wu, H. Wei, S. Sethuraman and A. C. Bovik, "Study of the Subjective and Objective Quality of High Motion Live Streaming Videos," IEEE Transactions on Image Processing, vol. 31, pp. 1027-1041, 2022.
- Z. Shang, J. P. Ebenezer, A. C. Bovik, Y. Wu, H. Wei and S. Sethuraman, "Assessment of Subjective and Objective Quality of Live Streaming Sports Videos," 2021 Picture Coding Symposium (PCS), 2021.

and acknowledge the source: Laboratory for Image and Video Engineering (LIVE), UT Austin. This project's README carries this citation in full — see the Data section there.

## synthetic_derived — generated streaming telemetry

**What it is:** Playback/QoE-style records (buffering, startup delay, session duration) generated by us to exercise the analytical architecture, because real session-level streaming telemetry (from any commercial streaming platform) is proprietary and not published anywhere, by anyone, ever — there is no legitimate way to obtain it publicly, and pretending otherwise would be the fabrication this whole document exists to prevent.

**Rule enforced in schema, not just prose:** `raw.qoe_observations.generation_method` is required (non-null) whenever `source_type = 'synthetic_derived'`. A synthetic row with no documented generation method is treated as a data-quality failure by the validation layer, not just a style nit.

---

Every number this platform's agent or dashboards produce traces back to exactly one of the four rows above. If a question can't be answered from real or honestly-labeled-synthetic data, the correct answer is "I don't have the data to answer that reliably" — not a plausible-sounding guess.
